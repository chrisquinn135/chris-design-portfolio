STATE FARM DESIGN SYSTEM

Modernizing the system for the next generation

Challenge

With more than a century of history, State Farm has evolved through many visual eras. Its previous design system, in place for eight years, had become constrained by legacy technology, accessibility gaps, and inconsistent user experiences. technology, accessibility gaps, and inconsistent user experiences.

I joined in 2024 at a pivotal moment, as the organization began reimagining its design system for the future.

Impact

I led the modernization of design system, redefining foundations, scaling components, and pushing the system beyond maintenance mode into a strategic platform for consistency, efficiency, and innovation.

Since the release of the new design system, adoption has expanded across product team, with ongoing enhancements in accessibility, tooling, and AI integration to ensure it continues to evolve alongside the organization’s needs.

01
Foundations

Starting with design tokens

I led the introduction of design tokens as the single source of truth for UI styling across the system. This reduced visual drift, improved design–engineering alignment, and created a scalable and consistent visual foundation.

For a deeper look at the implementation strategy, see the dedicated design token case study below.

Go to case study

Systemizing design decisions

I took this opportunity to redefine our design language using a systematic, math-driven approach. I established scalable rules for foundational elements that could be reliably extended across products.
Implementing tokens also unlocked theming and responsiveness across the system. We introduced structured token layers to support responsive spacing and typography, as well as light and dark themes.

Building in accessibility

Accessibility was built into the system from the foundational level. I embedded WCAG-compliant standards into system’s core elements to ensure accessible outcomes by default.

02
Components

40+ components redesigned and modernized

We rebuilt the component library from the ground up. Each component was audited and reviewed with product-area champions to identify inconsistencies, gaps, and scalability issues.

Components were re-architected using modern Figma build practices such as nested properties, boolean and text variables, and slots, creating flexible, reusable components that reduced duplication and improved implementation clarity.

Introducing data visualization and chat components

In addition to modernizing the existing components, we introduced several new components around initiatives such as data visualization and chat.

Channeling my inner developer

I had the opportunity to directly contributed to the design system codebase, submitting merge requests to bug fix and refine components in production.

This hands-on involvement strengthened design-engineer alignment and ensured parity between Figma architecture and the live component library.

03
Alignment and community

Documentation and design system education

Design system documentation is the first step to answering and documenting the work we were doing. We located on an internal website and provides users with guidance necessary to use the system effectively.

Documentation was written and published directly into HTML and Markdown, speeding up updates as well as providing cost-saving benefits from not using an external documentation platform.
In addition to written documentation, we recorded several tutorial videos on design system specific topics such as templating, mode swapping and token usage.

Office hours and design champions

Design systems work is as much about relationships as it is about code or components. During SFDS modernization, we held weekly meetings with product champions to consult, gather feedback, and ensure the system met real team needs. This collaboration drove meaningful outcomes:

  • Feedback influenced the Figma build or aesthetic design for 54% of components.
  • Feedback shaped functionality or documentation guidance for 71% of components.
  • Developed 10 new pattern guides to improve consistency, all informed by product team input.
Since the SFDS launch, we’ve expanded engagement with monthly release share-outs and bi-monthly office hours, while providing multiple channels for both designers and engineers to ask questions, give feedback, and stay aligned.

04
Design system tooling

Custom Figma plugins

I built several custom Figma plugins while at State Farm. These were aggregated into the State Farm Design System plugin, which served as the designer’s general toolkit when designing products. These functionalities included:

  • OneX Converter: Migrates styles and components from the legacy design system to the State Farm Design System (SFDS), reducing manual rework.
  • Design Linter: Scans designs to ensure correct usage of design tokens, preventing inconsistencies before handoff.
  • Color Selector: Helps designers quickly apply the correct SFDS color tokens in context, ensuring accessible and consistent color usage.

Code Connect and MCP agents

To prepare SFDS for the AI-driven design landscape, I implemented Code Connect for all system components. This mapping enabled automated code generation for engineers and integration with Figma’s MCP server, further streamlining handoffs and setting the stage for AI-assisted UI development.

Generative UI with Figma Make

After Figma’s Make launch at 2025 Config, I explored how generative UI could work within SFDS constraints. Initial attempts revealed gaps in design system integration, making outputs inconsistent. Through iterative testing and refinement, I developed the SFDS Make Template, which is now being piloted across the organization to enable reliable, AI-assisted design.
